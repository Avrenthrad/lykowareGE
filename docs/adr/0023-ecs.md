# ADR 0023 — The Lykoware entity-component system

Status: Proposed. The owner chose "write our own" on 2026-11-04; the design below waits for the owner.
Related task/PR: Phase 1 ECS, PR 1 (branch `claude/ecs-core`).
Supersedes / superseded by: none. Builds on [ADR 0021](0021-product-targets.md) (single-player built co-op-ready, so deterministic and command-driven).

## Context

The roadmap's Phase 1 needs an "ECS with stable IDs". The brief asks for a "data-driven ECS core handling hundreds of units". ARCHITECTURE.md left the design and library open.

ADR 0021 adds two needs:
- the same commands in the same order must give the same game state, for replays, saves and later co-op;
- every handle must be safe to keep, like the physics handles (ADR 0020).

## Options

The owner was asked on 2026-11-04:

- **Write our own** (chosen). Full ownership; built for determinism and safe handles from the start. More work now.
- **EnTT** (MIT). Very fast and widely used. Its heavy templates are hard to keep behind a Lykoware API, and the replay and save rules would still be ours to add.
- **flecs** (MIT). Rich features (relationships, scheduling, an inspector). The largest and most opinionated option; its way of running systems would shape the engine.

Storage designs considered for our own:
- **Sparse sets** (chosen for PR 1): one packed array per component type. Adding and removing components is cheap, and iterating one type walks contiguous memory.
- **Archetypes:** entities with the same set of components are stored together, so iterating several types at once is faster, but adding or removing a component moves the whole entity. This is worth revisiting with measurements if multi-component iteration becomes the bottleneck. The public API below does not expose the storage, so the switch would not affect callers.

## Decision

Proposed:

- **`lykoware::ecs::World`** in `engine/include/lykoware/ecs.hpp`, plus `engine/src/ecs.cpp` for the parts that are not templates. No third-party code.
- **Entities.** `Entity` is `{index, generation}`, like the physics handles.
  - Freed slots are reused last-freed-first with a new generation, so an old handle never reaches a new entity.
  - The default handle is never valid.
  - A slot whose generation would wrap round after 2^32 - 1 reuses is retired, not reused. The physics slot table does the same.
- **Components.** Any movable C++ type, at most one of each type per entity:
  - `add<T>(entity, args...)` builds one; `get<T>`, `has<T>`, `remove<T>` and `count<T>` do the rest.
  - `destroy(entity)` removes all of an entity's components.
  - Pointers from `add` and `get` stay valid until the next `add` or `remove` of that type.
- **Iteration.** `each<A, B, ...>(fn)` calls `fn(entity, a, b, ...)` for every entity that has all the listed components.
  - The order is the order of the A components in storage. It changes only when components are removed, and the same calls always give the same order.
  - While any `each` runs, structural changes (`create`, `destroy`, `add`, `remove`) are refused rather than corrupting the iteration. Reading and changing component values is allowed, and so are nested `each` calls.
  - A deferred-change buffer comes with the command bus.
- **Misuse is defined, never a crash.** Invalid, destroyed or foreign handles, duplicate components and refused changes return false, nullptr or the default handle. Nothing throws for misuse.
- **Determinism.** Nothing depends on addresses, hashing, time or thread timing. Component type numbers depend on the order types are first used in the process, but they only locate storage and never affect results.
- **Threading:** one thread at a time per world for now. Parallel systems come later, with measurements.

## Contracts and compatibility

- New public header `lykoware/ecs.hpp`; no other API changes.
- `World` is movable, not copyable. Components are owned by the world and destroyed with it, exactly once.
- Not yet: saving and loading (needs component descriptions, with the scene format), parent and child links, events, and systems scheduling. Each comes with its caller.

## Consequences

- Game code gets one way to store and update objects, with the same handle rules as physics.
- Templates live in the header, so changing the ECS recompiles its users.
- Removing a component moves another one, so code must not keep pointers across `add` or `remove` (documented on the class).

## Verification

- **New test `ecs.world`** (links only the engine):
  - **Handles:** the default is invalid; destroyed handles stay invalid; slots are reused last-freed-first with new generations; out-of-range and wrong-generation handles fail.
  - **Components:** add, get, has, remove and count; duplicates refused; destroyed or stale handles never see components, even when their slot was reused by an entity that has the same component type.
  - **Lifetime:** destroying an entity destroys all its components; a moved world keeps its entities; destroying the world destroys every component exactly once (counted with a component that tracks its own instances).
  - **Packed storage:** after removals from the middle, every entity still finds its own values, and iteration visits exactly the remaining ones.
  - **Iteration:** with one, two and three component types; values can be changed; combinations nobody has visit nothing.
  - **Changes during iteration:** create, destroy, add and remove are refused; reads and nested iteration work; changes work again after `each` exits, even by an exception.
  - **Determinism:** 5000 scripted random operations run twice give the same handles, values and iteration order.
  - **Scale:** three rounds of 20,000 creates and destroys leave nothing behind and reuse slots.
- **Deliberate breaks, each caught:**
  - ignoring generations;
  - a packed-storage removal that forgets to update the moved entry;
  - `destroy` keeping components;
  - allowing `add` during iteration;
  - reusing slots first-freed-first;
  - letting `each` visit entities that lack one of three components. This break first passed, because no test used three component types; the three-component check was added and now catches it.
- **Not tested:** retiring a slot after 2^32 - 1 reuses, which would take billions of operations. The rule is three lines in `World::destroy`.
- **Benchmark `perf.ecs_iterate_100k`:** a movement system (position += velocity × dt) over 100,000 entities for 300 frames. Provisional and CPU-only; the limit is 250 ms per frame, slack for Debug and sanitizer builds.
- **Local results:**
  - 34/34 tests pass in the Debug, ASan/UBSan and clang-tidy presets.
  - Benchmark, GCC 13 Release, one thread: the movement system costs about 4 ns per entity. 1000 entities take 0.005 ms per frame, 100,000 take 0.39 ms and 1,000,000 take 3.9 ms. Hundreds of units, the brief's target, cost well under a microsecond each frame. Debug: 63 ns per entity.
- **CI:** pending.
